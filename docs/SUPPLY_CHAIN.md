# Supply chain: locks, licences, SBOM, bundle and signatures

Tripline Scope installs from an offline bundle and never touches the network at runtime: no telemetry,
licence calls or update checks. This document describes how the bundle is built from pinned, hash-checked
open-source components, how licences are enforced, and how a hospital verifies what it received. All
commands run on the vendor's build machine unless stated otherwise; `make help` lists the targets.

## 1. Dependency locks

| File | Contents | Generated by |
|---|---|---|
| `requirements/runtime.txt` | runtime closure of `tripline-scope` + `tripline-scope-verify` (41 packages) | `make lock` |
| `requirements/dev.txt` | runtime + pytest, ruff, cyclonedx-bom, httpx (79), constrained to the runtime pins | `make lock` |
| `requirements/build.txt` | pip, setuptools, wheel, packaging: build machine only | `make lock` |
| `requirements/local.in` | `./verify`: the first-party verifier, never resolved from an index | hand-written |
| `requirements/native-audit.json` | native components inside the runtime wheels (section 4) | `make native-audit` |

* `scripts/lock.sh` runs `uv pip compile --generate-hashes --python-version 3.12 --python-platform
  x86_64-manylinux_2_28`. Every entry is pinned with `==` and carries the SHA-256 of every published
  artefact of that version. Existing pins are kept as preferences; pass `--upgrade` / `--upgrade-package`
  through `scripts/lock.sh` to move them.
* **First-party packages are never resolved from PyPI.** `pyproject.toml` requires
  `tripline-scope-verify==0.1.0`; during locking that requirement is satisfied by `./verify` and then
  excluded from the output. The bundle pins both first-party wheels by the hash of the wheel built here,
  and installs with `--no-index`, so a package of the same name on a public index cannot be substituted.
* Checks: `make check-locks` (also a test and a CI step) fails unless every entry is pinned and hashed,
  the runtime lock covers both `pyproject.toml` files and the dev lock agrees with the runtime pins. CI
  also re-runs `make lock` and fails if the files change.
* Runtime wheels are fetched with `pip download --only-binary=:all: --require-hashes` for CPython 3.12,
  `manylinux` x86_64 (`scripts/fetch_wheels.sh`). A package without a suitable wheel fails the build
  rather than building an sdist with unpinned build dependencies. `cryptography` and `pyarrow` ship only
  `manylinux_2_28` wheels, so **venv mode needs glibc 2.28 or later** (RHEL/Rocky 8+, Debian 10+, Ubuntu
  20.04+).
* Our two wheels are built from the files tracked by git, offline, with the hash-pinned build tools and no
  build isolation; `SOURCE_DATE_EPOCH` is the last commit time, so the same commit gives byte-identical
  wheels (checked: two builds produced identical SHA-256).

## 2. Licence policy and gate

Runtime dependencies must be **MIT, MIT-0, BSD-2-Clause, BSD-3-Clause, Apache-2.0, ISC or PSF-2.0**. LGPL is
allowed only for unmodified, dynamically linked libraries listed by name in `LGPL_EXCEPTIONS` (currently
**none**). GPL, AGPL, SSPL, unknown or missing licences fail. Telemetry SDKs and exporters
(`opentelemetry-sdk`, `opentelemetry-exporter-*`, `sentry-sdk`, `ddtrace`, ...) fail whatever their
licence.

`scripts/check_licences.py` (`make licences`; CI job `licences-sbom`):

1. Takes the closure from the lock and the distributions from the wheels (`--wheels`) or an installed
   site-packages (`--site-packages`). Every locked package must be present at the locked version, and
   nothing else may be (first-party packages excepted).
2. Resolves each licence in order: `License-Expression` (PEP 639), the `License` field (aliases or SPDX),
   trove classifiers (a "BSD License" or "Apache Software License" classifier is resolved to a variant from
   the shipped licence text), then the licence text itself. SPDX `OR` passes if any branch is allowed
   (the licensee chooses); `AND` needs every branch. A copyleft classifier that the resolved expression
   does not mention is a conflict and fails.
3. Scans every licence-like file bundled anywhere in each distribution for GPL/LGPL/AGPL/SSPL licence texts
   or grants (a mention, such as the PSF licence history table, is not a grant). Reviewed files are cleared
   only through `BUNDLED_FILE_EXCEPTIONS`.
4. With `--native-audit`, evaluates the Rust crates statically linked into native wheels (section 4).
5. Writes a machine-readable report (`--json-out`, schema `tripline.licence-check/v1`) and exits 1 on any
   failure, 2 on a usage error.

## 3. Native and bundled components

Wheels with compiled code carry code that is not visible in Python metadata.
`scripts/audit_native.py` (`make native-audit`) records, per native wheel, the extension modules, the shared
libraries auditwheel bundled, and the licence files shipped. For Rust extensions it lists crates from:

* **`Cargo.lock` in the PyPI sdist**, where the sdist's SHA-256 matches the lock (cryptography,
  pydantic-core). It covers every target and feature, so it is a superset of what is linked.
* **The crates.io archive of the Rust `evtx` crate.** The Python `evtx` 0.13.1 publishes no sdist. The
  version linked (0.12.3) is read from the binary, and the archive is checked against the crates.io
  checksum.
* **Crate source paths embedded in the shipped `.so` files.** This is evidence that a crate is actually
  linked, but only a lower bound.

Crate licences come from crates.io. The result is committed, and the gate fails if it is stale for the
locked versions, if a native wheel has no entry, or if any crate is copyleft or has no licence.

## 4. SBOM

`make sbom` (and every `make bundle`) runs `cyclonedx-py environment` against a **clean virtualenv
installed offline from the bundle's wheels with `--require-hashes`**, so licences come from installed
metadata. `scripts/sbom.py` then adds, to every component (the root `tripline-scope` included):

* the SHA-256 of the exact wheel shipped, which must be one of the lock's hashes;
* the wheel's path in the bundle;
* its origin (PyPI pinned by hash, or first-party);
* nested components for the Rust crates seen in the binary (`pkg:cargo/...`) and for auditwheel-bundled
  libraries.

`sbom.py check` (a test and a CI step) fails unless every locked runtime dependency appears with the locked
version, a `pkg:pypi` purl, a lock-listed SHA-256 and a licence; both first-party packages are present with
hashes; and nothing outside the lock is listed. Output: CycloneDX 1.6 JSON, `sbom.cdx.json` in the bundle.

What `install.sh` does: it checks every file against `SHA256SUMS` and refuses unlisted files. It then checks
the release signature with OpenSSL ≥ 3 against a release key id supplied out of band
(`--release-key-id`); this happens **before any bundled code runs**. Only then does it install:

* **venv mode:** `pip install --no-index --find-links wheels --require-hashes -r requirements.txt` into a
  Python 3.12 virtualenv, followed by pruning;
* **container mode:** `docker load`, plus the compose file and an `.env` template.

`smoke-test.sh` runs a synthetic installation qualification in a throw-away directory.

## 6. Signature and verification

`SHA256SUMS` lists `<sha256>  <relative path>` for every other file in the bundle. `SHA256SUMS.sig` is a
`tripline.signatures/v1` document (RFC 8785 canonical JSON) with one `release` signature: Ed25519 over the
exact bytes of `SHA256SUMS`, naming the signed file, the key id and the public key. The key id is the first
32 hex characters of SHA-256 over the raw 32-byte public key.

Verify on any machine:

```
tscope-verify checksums SHA256SUMS --sig SHA256SUMS.sig --key release.pub     # or: make bundle-verify
```

`release.pub` inside the bundle proves integrity, not origin. Compare its key id with the id the vendor gives
you out of band, or verify against a copy of the key you already trust. Without Python:

```
openssl pkey -pubin -in release.pub -outform DER | tail -c 32 | sha256sum | cut -c1-32      # key id
sed -n 's/.*"signature":"\([^"]*\)".*/\1/p' SHA256SUMS.sig | base64 -d > sig.bin
openssl pkeyutl -verify -pubin -inkey release.pub -rawin -in SHA256SUMS -sigfile sig.bin
sha256sum -c SHA256SUMS
```

The stand-alone verifier needs only `cryptography` and `rfc8785`. A test installs it alone (offline,
hash-checked) and uses it to verify report chains, audit logs, destruction certificates and signed
checksums produced by the full product. The same test proves it never imports `tripline_scope`.

## 7. Container images

* **App image.** Based on `mirror.gcr.io/library/python:3.12-slim`, pinned by digest in the `Dockerfile`
  (override `PYTHON_IMAGE` to use a hospital mirror). It installs only from the bundled wheels with
  `--no-index --require-hashes`, removes pip, and runs as uid 10001. Compose runs it with a read-only root
  filesystem, all capabilities dropped and `no-new-privileges`.
* **PostgreSQL.** `mirror.gcr.io/library/postgres:16` by default (`TSCOPE_POSTGRES_IMAGE` overrides). It
  never logs SQL text: `log_statement=none`, `log_min_error_statement=panic`.
* **Base-image OS packages** (Debian 13 in the Python and PostgreSQL images) are aggregated system
  components. They run alongside the product but are not linked into it, and the Python licence gate and
  SBOM do not cover them: the SBOM covers the Python runtime closure, and `images/IMAGES.txt` records the
  digests. A hospital that wants an OS-level inventory can scan the loaded images with its own tooling.
* **SQL Server Developer Edition** is licensed for development, test and demonstration only. It is used
  only under the compose `demo` profile, for synthetic data, and needs `TSCOPE_MSSQL_ACCEPT_EULA=Y`. Real
  `.bak` restores go to a SQL Server the hospital provides and licenses.

## 8. Release key management and rotation

* **Generation.** Generate the release key offline on the release officer's machine, and keep it on
  encrypted removable media, never in the repository:
  `tscope keys generate --role release --out /media/release-keys`, with a strong passphrase in
  `TSCOPE_RELEASE_KEY_PASSPHRASE` or at the prompt.
* **Signing.** Set `RELEASE_KEY=/media/release-keys/release_signing.pem` and `RELEASE_KEY_PASSPHRASE`, then
  run `make bundle`. CI signs tags with the `RELEASE_KEY_PEM` and `RELEASE_KEY_PASSPHRASE` secrets.
* **Ephemeral keys.** Without `RELEASE_KEY`, `scripts/sign_release.py` generates an **ephemeral key** in a
  new directory under the system temp dir, outside the repository, and prints a warning.
  `BUILDINFO.json` then records `"release_key": "ephemeral"`. Such bundles are for testing only.
* **Publishing the key id.** Publish the key id to each hospital out of band (handover letter, phone
  read-back). Hospitals pass it to `install.sh --release-key-id`.
* **Rotation.**
  1. Generate the new key.
  2. Write `KEY-ROTATION.txt` naming the new key id and its effective release.
  3. Sign that file with the old key (`openssl pkeyutl -sign -rawin -inkey old.pem -in KEY-ROTATION.txt`),
     and deliver it with the next bundle and through the out-of-band channel.
  4. Hospitals verify it with the old key they already trust before accepting the new key id.
  5. Destroy the old private key after the transition release.
* **Compromise.** There is no online revocation in an air-gapped estate. Notify every hospital out of band,
  publish a new key id, and re-sign current bundles with the new key.

## 9. Updating dependencies

1. `make lock` (with `--upgrade-package NAME` passed through `scripts/lock.sh` to move a pin).
2. `make wheelhouse native-audit licences sbom`.
3. Review `git diff requirements/`, any new `native-review` lines, and new bundled licence files.
4. Run `make test`, then `make bundle install-test`.

Whenever another track adds a runtime dependency to `pyproject.toml`, re-run step 1, commit the regenerated
locks and audit, and the gate re-evaluates the new closure.
